# Initial Specification

This document is a cleaned and translated version of the raw transcript of a recorded audio describing the draft specification of a software system.

## Overview

The goal is to design an agentic system compatible with most of the current standards and protocols:

- **ACP (Agent Communication Protocol)** — for communication between the agentic system and an IDE.
- **A2A (Agent-to-Agent Protocol)** — for communication between the agentic system and other systems.
- **MCP (Model Context Protocol)** — for managing external tools and resources.
- **AG-UI** — for streaming between the agentic platform and a web user interface; it defines the format of the messages sent by the agent during its inference.

To ensure a viable implementation, it is essential to study each of these protocols thoroughly and to respect full compliance of the implementation. This requires a complete study phase or pre-generating the documentation of the APIs concerned.

## User Privileges

User privilege management is based on a classic **RBAC** (Role-Based Access Control) system:

- Roles are linked to permissions.
- Users are assigned roles.

Users holding administrative roles can:

- Create, delete, and administer other users.
- Create and administer roles and permissions, in order to manage the platform.

Users with the appropriate permission can also create and administer **personal API keys** linked to their account. These API keys:

- May have a limited lifetime.
- Are created with a subset of the user's permissions.
- Allow using the application's API while authenticated.

## Use Cases

### 1. Agent Creation

An agent groups together a system prompt and the set of tools authorized during a session.

There are also basic tools that allow reading files, writing files, and performing certain actions on files. For file-management tools, the reference is what is done, for example, in **Codex** or in the reference MCP server called **MCP FileSystem**.

The definition of an agent consists of:

- Its name.
- A short description of its intent and the capabilities it is given.
- Its system prompt.
- The tools it has access to.
- Optionally, whether it is able to create sub-agents.
- The LLM model it is linked to.

To provide a better user experience, it is also possible to attach a photograph to an agent. By default, this photograph is generated from the Python library **RoboHash** or an equivalent. (If the RoboHash library is used, or images coming from this library, the copyright notices related to this library must be added.)

### 2. LLM Configuration

The second use case, generated by the first, is the ability to configure LLMs.

First, a **provider** is chosen. Providers can be of several types depending on the API they implement:

- An LLM implementing the legacy **OpenAI** API (V1 Completion).
- An LLM implementing the **OpenAI Responses** API.
- A direct implementation of the **Anthropic** API called **Messages**.

If a **generic provider** is chosen, one selects the base URL, the API key, and the type of API it conforms to. Some providers also expose an endpoint to retrieve the list of model names usable for that provider.

Beyond generic providers, the application also allows selecting certain **known providers** and adapting to the particularities of their APIs. For example:

- **Moonshot** — its API URL is pre-filled; the `Moonshot API Key` environment variable can be used as the API key value; the list of available models is retrieved via the Moonshot API endpoint.
- **DeepSeek** — its URL is pre-filled; the environment variable can be defined; the models are those of DeepSeek.

### 3. Starting a Session on a Project

The user designates a project as a folder on their PC. Then, they choose an agent and get a chat-type interface where they can ask questions. The agentic session uses its tools while respecting the concerned project's folder.

The interface displays, on the left, a kind of tree whose roots are the projects and, below, the various sessions created for the considered project.

The chat window is compatible with the **AG-UI** protocol. At the bottom, it displays a classic input form that allows, optionally, adding attachments via a paperclip-type icon.

It is possible to use the **Web Audio API Speech-to-Text** to facilitate input by speaking, via a microphone-type icon.

The interface also provides autocompletion:

- When the user types a slash (`/`), a combo box autocompletes the various installed **skills** (skills are discussed later).
- The `@` character autocompletes filenames relative to the project root.

When the user finishes typing and sends their message, the session starts and the agent produces tokens that are streamed. The agent's reasoning is visible. Markdown characters are interpreted. Code blocks that are **Mermaid** are also interpreted, i.e. the diagrams are displayed.

However, the source code of these elements can be copied via small icons in the top-left corner that allow the user to copy to the clipboard the source code of either the diagrams or the Markdown. The component that displays Mermaid diagrams also allows panning, zooming in and out, etc., to make the display more pleasant.

In this direct-usage mode, the session is linked to the current user interface: if the user closes their browser page, the session ends. However, the user can resume an existing session by selecting it from the left menu and asking a new question. Since previous questions are visible in the chat, the user can also edit one of these previous questions; the conversation then restarts from the last edited question.

During a session, the user can change the current agent's mode. For example:

- An **Ask** mode, in which the filesystem write tools are disabled.
- An **Agent** mode, which has the full set of tools.

The modes are defined in advance for an agent in the agent configuration interface.

### 4. Use via the ACP Protocol

In this case, an external IDE uses the application, probably via an RPC protocol over STDIO. The external IDE starts and manages sessions in the way closest to what could have been managed directly via the application's user interface.

### 5. Use via the A2A Protocol

In this last case, the A2A API — used via the authentication of an API key created in advance — allows starting an agentic session.

Only certain agents must support the A2A protocol: specifically, those that have been designated as such and for which the user who created them has added a specific **agent card**.

## MCP Apps

The **MCP Apps** extension allows producing user interfaces coming from the MCP servers being used.

In the application's interface, MCP apps must be supported. When an app is used, it is displayed in a set of tabs placed on the **left** of the agentic conversation, rather than inside the conversation flow. This way, it is easier for a user to navigate the tabs and view the conversation at the same time.

## Research Requirements

Before starting any study or implementation, one must thoroughly document the various libraries and protocols mentioned, notably **A2A**, **MCP**, **MCP Apps**, **AG-UI**, and others.

It is also important that the system for managing agent avatar photos be complete, notably the use of **RoboHash** by default. The images must come from **RoboHash set number 1**. It is not permitted to reproduce or imagine any other system than this one.

## Technical Stack

- The agentic harness is implemented in **Python** using the **Pydantic AI** library.
- The various agents, models, settings, etc., must absolutely be stored in a **SQLite** database.
- Use **asynchronous code** whenever possible.
- The backend is implemented using notably **FastAPI**, **SQLModel**, **loguru**, etc.
- The project is a **monorepo** managed by **Uv Workspaces**.
- The user interface uses **React**, with **Mantine** components.
- **Light** and **Dark** modes by default, following the system setting.
- CSS framework: **Bulma**.
- Icons come from the **RemixIcons** library.

The ease of use and the user interface in general must be ambitious and easy to develop: precise component division, message mediation via a bus, no oversimplification — the goal is a pleasant and ambitious user interface.

Compliance with the various protocols cited is absolutely mandatory and must under no circumstances be replaced by homegrown code.
