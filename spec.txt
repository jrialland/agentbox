Il s'agit de réfléchir à la mise au point d'un système agentique compatible avec la plupart des standards et protocoles actuels.À savoir pour la communication entre le système agentique et un IDE, le protocole Agent Communication Protocol ACP.
Et pour la communication entre système agentique et d'autres systèmes éventuels, le protocole A2A, c'est-à-dire Agent to Agent Protocol.
Également pour la gestion éventuelle d'outils externes et de ressources, le protocole MCP.
Enfin, pour la mise en place éventuelle de streaming entre la plateforme agentique et une interface utilisateur web, le protocole AG-UI Qui définit le format des messages envoyés par l'agent pendant son inférence.
Afin de permettre une implémentation qui soit viable, il sera très important de se documenter sur l'édit protocole et de respecter la conformité de l'implémentation pour qu'elle soit totale.Et donc de procéder à une phase d'étude complète ou de générer à l'avance la documentation des API concernées.

La gestion des privilèges utilisateurs se fait au moyen d'un système RBAC classique, c'est-à-dire avec des rôles, les rôles étant liés à des permissions et les utilisateurs ayant des rôles.

Les utilisateurs possédant les rôles d'administration peuvent venir créer, supprimer et administrer d'autres utilisateurs, créer et administrer des rôles et des permissions dans le but de gérer la plateforme.

Les utilisateurs dotés de la permission adéquate peuvent également venir créer et administrer des clés d'API personnelles liées à leur compte. Ces clés d'API qui peuvent avoir une durée de vie limitée dans le temps et qui sont créées avec un sous-ensemble de la liste des permissions de l'utilisateur. elles Permettent d'utiliser l'API de l'application en étant authentifié.

Les cas d'usage basiques sont les suivants.

Le premier cas d'utilisation est la création d'agents, c'est-à-dire qu'un agent regroupe un prompt système ainsi que l'ensemble des outils autorisés pendant une session. Il y a également des outils de base qui permettent. De venir lire des fichiers, écrire des fichiers et effectuer certaines actions sur des fichiers. Pour les outils de gestion de fichiers, on regardera du côté de ce qui est fait par exemple dans Codex ou le serveur MCP de référence qui s'appelle MCP FileSystem tout simplement.

La définition d'un agent est donc son nom, une courte description de l'intention des possibilités qu'on lui donne, ainsi que son prompt système, les outils auxquels il a accès, éventuellement sa capacité ou non à créer des sub-agents, et également le lier à un modèle LLM.

Pour permettre une meilleure expérience utilisateur, il est également possible d'attacher à un agent une photographie qui, par défaut, est générée à partir de la librairie Python Robohash ou un équivalent.(Si la librairie RoboH est utilisée ou les images provenant de cette librairie, ne pas oublier d'ajouter les notices de copyright afférentes à cette librairie.)

Le deuxième cas d'utilisation qui est généré par le premier est la possibilité de configurer des LLM. Pour ce faire, on va d'abord choisir un provider. Les providers peuvent être de plusieurs types en fonction de l'API qu'ils implémentent. Soit il s'agit d'un LLM qui implémente l'API Legacy d'OpenAI, c'est-à-dire V1 Complétion.Soit il s'agit d'un LLM qui implémente l'API OpenAI Responses, ou alors l'implémentation directe de l'API d'Antropic qui s'appelle Messages. Si on choisit un provider générique, on va donc choisir l'URL de base, l'API key ainsi que le type d'API à laquelle il se conforme. Certains providers disposent également d'un endpoint qui permet de récupérer la liste des noms de modèles qui sont utilisables pour ce provider.Au-delà des providers génériques, l'application permet également de sélectionner certains providers connus et ainsi de s'adapter aux particularités de leurs API. Par exemple, si on choisit le provider Moonshot, l'URL de son API est déjà pré-rempli. On peut également utiliser. La variable d'environnement Moonshot API Key en guise de valeur pour l'API Key et également avoir la liste des modèles disponibles via le endpoint de l'API Moonshot.

Même chose pour DeepSeek, si on choisit le provider DeepSeek, l'URL est déjà remplie, la variable d'environnement peut être définie et les modèles sont ceux de DeepSeek.

Le troisième cas d'utilisation est le démarrage d'une session proprement dite sur un projet. L'utilisateur désigne un projet comme étant un dossier sur son PC. Ensuite, il choisit un agent et il dispose d'une interface de type chat dans laquelle il peut poser des questions. Et la session agentique va utiliser ces outils en respectant le dossier du projet concerné. L'interface affiche à gauche une sorte d'arbre dans lequel les racines sont les projets et ensuite en dessous les différentes sessions qui ont été créées pour le projet considéré.La fenêtre de chat est compatible avec le protocole AGUI. Elle fait apparaître en bas Un formulaire de saisie classique qui permet éventuellement d'ajouter des pièces jointes avec une icône de type trombone, par exemple.Possibilité d'utiliser l'API Web Audio Speech2Text pour faciliter la saisie en parlant avec une icône de type micro.L'interface permet également la complétion automatique : Par exemple, quand l'utilisateur tape slash, une combo box permet l'autocomplétion des différents skills installés. (Nous reviendrons sur les skills plus tard.) Le caractère « arrow base » permet la complétion des noms de fichiers relatifs à la racine du projet.

Quand l'utilisateur a terminé sa saisie et envoie son message, la session démarre et l'agent produit des tokens qui sont streamés. Le raisonnement de l'agent est visible.Les caractères Markdown sont interprétés. Les blocs de code qui sont du mermaid sont également interprétés, c'est-à-dire que les diagrammes sont affichés.Toutefois, le code source de ces éléments peut être copié au moyen de petites icônes dans le coin en haut à gauche qui permettent à l'utilisateur de venir sélectionner dans le presse-papier le code source, soit des diagrammes, soit du Markdown. Le composant qui affiche les diagrammes mermaids permet en outre de se déplacer, zoomer, dézoomer, etc., de manière à pouvoir rendre l'affichage plus agréable.

Dans ce mode d'utilisation directe, La session est liée à l'interface utilisateur courante, c'est-à-dire que si l'utilisateur ferme la page de son navigateur, la session se termine.Il est toutefois possible pour l'utilisateur de reprendre une session existante en la sélectionnant dans le menu de gauche et poser une nouvelle question.Puisque ces anciennes questions sont visibles dans le chat, il lui est également possible de venir éditer une de ces anciennes questions. À ce moment-là, la conversation repart de la dernière question qu'il a éditée.

Pendant une session, l'utilisateur peut changer le mode de l'agent courant, c'est-à-dire, par exemple, un mode Ask Dans lequel les outils d'écriture dans le système de fichiers sont désactivés, et un mode agent qui a l'ensemble des outils. Les modes sont définis pour un agent dans l'interface de configuration des agents à l'avance.

Le quatrième cas d'utilisation est l'utilisation via le protocole ACP.  Dans ce cas, c'est un IDE externe qui vient utiliser l'application, probablement via un protocole RPC over STDIO. L'IDE externe démarre et gère les sessions de la façon la plus proche de ce qui aurait pu être géré via l'interface utilisateur de l'application, directement.

Dernier cas d'utilisation, l'utilisation via le protocole A2A. Dans ce dernier cas, l'API A2A utilisée via l'authentification d'une API qui est créée à l'avance Permet de démarrer une session agentique. Seuls certains agents doivent supporter le protocole A2A. Il s'agit des agents que l'on a spécifiquement désignés comme tels et pour lesquels l'utilisateur qui les a créés a ajouté une agent card spécifique.

L'extension MCP Apps permet de produire des interfaces utilisateurs provenant des serveurs MCP que l'on utilise.Je souhaite que dans l'interface de l'application, les MCP apps soient supportés. Je souhaite que quand une app Et elle s'affiche dans un ensemble d'onglets qui se mettent sur la gauche de la conversation agentique et non pas dans le flux de la conversation. De cette façon, il est plus aisé pour un utilisateur de naviguer. Les onglets et voir la conversation en même temps.

Avant de démarrer la moindre étude ou implémentation, tu veilleras à te documenter de manière extensive à propos des différentes librairies et protocoles qui ont été évoqués, notamment A2A, MCP, MCP Apps, AGUI et autres.

Il est également important que le système de gestion des photos d'avatars des agents soit complet, notamment l'utilisation de RoboHash par défaut. Les images doivent provenir du set numéro 1 de RoboHash. Il ne t'est pas possible de reproduire ou d'imaginer un autre système que celui-là.

L'implémentation du harnais agentique se fera en Python en utilisant la librairie Pydantic AI. Les différents agents, modèles, paramétrages, etc., doivent absolument être stockés dans une base de données SQLite. Utilisation de code asynchrone dès que possible. 

Le back-end est implémenté en utilisant notamment FastAPI, SQLModel, loguru, etc..

Le projet est un monorepo géré par des Uv Workspaces.

L'interface utilisateur utilise React. Les composants Mantine. Mode Light et Dark par défaut, qui suivent le paramétrage du système. Framework CSS Bulma. Les icônes proviennent de la librairie RemixIcons. 
La facilité d'utilisation et l'interface utilisateur en général doit être ambitieuse et facile à développer. Division en composants précis, médiation de messages via un bus, pas de sursimplification, car je veux une interface utilisateur agréable et ambitieuse.

La conformité aux différents protocoles cités est absolument obligatoire et ne doit surtout pas être remplacée par du code maison.
